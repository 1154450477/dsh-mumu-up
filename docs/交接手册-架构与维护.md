## 一、项目定位（一句话）

**dsh-mumu-up 是一个 DeepSeek Harness（DSH）第三方插件：定时用本地随机数（不花模型 token）掷骰子，掷中就往目标会话送一条"我玩会儿手机去"的用户消息，让 DSH 的 agent 自己开一轮、自己决定要不要调 mumu-mcp 的工具去玩 MuMu 模拟器。**

判定算法（峰谷命中线 / 没中加成 / 时机因子 / 安静时段 / 冷却）与 [dsh-speak-up](https://github.com/Yuuyuko-uu/dsh-speak-up) 逐条对齐，唯一区别是掷中后的动作：speak-up 是"找她搭话"，本插件是"叫她去玩手机"。配套的 MCP server 是 [dsh-mumu-mcp](https://github.com/1154450477/dsh-mumu-mcp)（本机控制口 `http://127.0.0.1:8791`）。

不是"上传/启动/备份工具"，与 MuMu 的关系只是：唤醒动作指向玩手机，并通过 8791 控制口问"手机是不是正在玩"。

## 三、总体架构与数据流

### 3.1 数据流（核心一条线）

```
宿主启动 → cordis.patch.yml 注册 id=mumu-up → lib/host.js apply(ctx)
  ├─ ctx.effect: 换表(配置.间隔分钟) → ctx.interval 每 N 分钟触发 掷一次('定时','自动')
  │     1. 读配置 (%USERPROFILE%\.dsh\mumu-up-config.json)
  │     2. 闸门依次判断：总开关 → 安静时段 → 有没有勾目标会话
  │     3. 挑目标：配置.目标会话 里排除已归档(workspaceRegistry)/没活着/忙(status!=='idle')的，随机挑 1 个
  │     4. 问手机：fetch 控制口 /state（3 秒超时；问不到当"没在玩"）
  │     5. 闸门：手机冷却分钟（距 last_played_ts）→ 手机忙时跳过（mode.active||playing）
  │     6. 掷骰：掷值 = Math.random()*100，命中线 = min(100, 档位命中线×时机因子 + min(加成上限,连没中×没中加成))
  │     7. 掷中 → 连没中=0 → 构造 user 消息(source.kind='mumu-up') → await agent.followup(消息) → sessions.flush()
  │        没中 → 连没中+=1，只记账
  └─ ctx.webServer.register 4 条路由 → 网页半边 fetch 读写
        GET  /dsh-mumu-up/state        # 配置+会话清单+日志一把给齐
        POST /dsh-mumu-up/save         # 合并保存（只覆盖传上来的字段）；间隔变了立刻换表
        POST /dsh-mumu-up/roll         # 手动'演练'/'真发'（走同一个掷一次()，不是另写一份）
        POST /dsh-mumu-up/new-session  # 通过 sessionController.create 新建"小屋"会话，可选追加勾上
```

### 3.2 网页半边（client.js）与宿主的分工

- client.js **不发消息、不掷骰**，只往上面 4 条路由读写；业务逻辑只有 host.js 一份。
- 通过 `window.__ModuleLoader__.load({ id:'dsh-mumu-up', factory })` 加载，`slots.inject('settings.section', …)` 把设置页挂进 **DSH 设置 → 插件 → 手机唤醒器**（order 54）。
- 交互约定：**勾选目标会话立即自动保存**（只发 `{目标会话}` 补丁，/save 是合并语义不会覆盖别的字段）；数字/文案改动置"脏"，渲染悬浮保存条（sticky bottom，脏才渲染）。

### 3.3 为什么触发消息必须是 user 角色（硬限制，别想改）

文件头 `lib/host.js:16-33` 有三条源码证据，结论：`agent.followup()` 收到的消息在 dsh-agent-loop 里被硬写成 `user/message` 事件；dsh-session 的 `validateSessionEventData` 会拒绝"user/message + developer 角色"；且 developer 消息在 dsh-llm 里会被 `withoutDeveloperMessages()` 从发给模型的请求里摘掉。所以：
- 送的是 `role:'user'` + `source:{kind:'mumu-up'}` 的消息（配置项`角色`仍存在，但填 `developer` 时插件**主动拒发并记账**，host.js:724-728）。

### 3.4 与 mumu-mcp 的关系

- 唤醒只是"说一句话"；真开手机是 agent 自己调 `mumu_phone_play`。
- 控制口 `/state` 返回 `{ mode:{active}, playing, last_played_ts }`（秒级时间戳，收手不清零；`last_play_ts` 会清零，只作兜底，host.js:544）。
- **装了本插件就不要开 mumu-mcp 的 `autoplay_enable`**（两套调度会重复叫她玩）；`mumu_phone_autoplay schedule` 定时计划不受影响。

## 六、维护手册（改代码 → 测试 → 部署 → 重启）

1. host.js / client.js 全是中文标识符的 ESM，无构建步骤、无第三方依赖，直接改即可。
2. 改配置项时三处必须同步：`默认配置`（host.js:98）、`归一化`（host.js:200）、设置页控件（client.js Section）+ `tests/网页半边.mjs:147` 的"要有"清单。

4. 改峰谷规则要同步 host.js:293-310 的注释和判峰时测试；**时段是写死的，不要加日期表**（用户明确要求）。

- 卸载靠 Cordis effect 清理（host.js:1196-1199 收摊停表），插件卸载即可，无残留进程。
- DSH 重启后内存里的"连没中"归零（设计如此，不是 bug）。

### 6.5 已知坑与陷阱（踩过的，别再踩）

1. **测试依赖真实时间**：`tests/宿主半边.mjs` 若在安静时段（默认 1~8 点）跑，5 条"时机因子/命中线"用例会被"安静时段这轮不掷"挡下而 FAIL。峰谷部分已喂假时间规避，但安静时段那几条没有。对策：改机器时间不稳妥，可临时 `/save` 覆盖 `安静起/安静止` 为当前小时再跑（或以后把安静判断也改成可注入时刻——见"可改进"）。
2. **followup 必须 await**：不接住 rejection，Node 22+ 视为致命错误会**带走整个 DSH 宿主进程**（host.js:747-750，2026-10-21 有用户报障）。换表 finally 里同理要吞错（host.js:788-792）。
3. **会话 id 前缀**：`session-` 前缀有时带有时不带，`找agent`/投影缓存文件名都是**两种候选都试**（host.js:415、886）；只试一种就会全退化。
4. **改名兼容必须看原始对象**：合并默认值后新键永远"存在"，旧键永远读不到（host.js:163 注释，测试真踩过）。
5. **设置页保存语义**：/save 是合并（只覆盖传入字段）；client.js 自动保存只发补丁、响应只刷服务端字段，防止抹掉未保存的别的改动（client.js:287-295）。
6. **间隔改动要立刻换表**：只改配置不重挂定时器，15 分钟改成 1 分钟也得干等满 15 分钟（host.js:1126-1137）。
7. **inject 硬依赖 sessionTitle**：用 `ctx.get()` 软拿时该服务全空；写进 inject 才有效。没有该服务的部署会装不上——删 inject 里那一项即可降级到投影缓存那条路（host.js:51-55、846-851）。
8. **角色 developer 送不了**（见 3.3）；别尝试"修好"它，那是 DSH 上游行为。
9. **mumu-mcp 的 autoplay_enable 别开**，否则双调度重复唤醒。
10. **安静时段会盖住谷时**：1~8 点安静时，谷时命中线再高也没用（设置页有红字提醒）。
11. **掷中只在"一个"目标会话里唤醒**：多勾等于分身+多份 token，是有意设计。
